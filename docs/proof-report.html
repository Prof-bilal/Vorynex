Measured evidence

Vorynex contains the damage.
It does not need to recognise the attack.

Four phases of measurement: a deliberately vulnerable fixture, a real third-party application, a request-layer WAF as the comparison arm, and the cost of each. Every number below comes from a run committed to the repository.

kernel 7.2.8 · Landlock ABI 10 · OWASP CRS 4.0 (pinned) · Coraza v3.8.1 · node 22.23.4

The claim. These attacks land when nothing is enforcing, and are contained when Vorynex is — while legitimate requests keep working. A request-layer filter stops the payloads it recognises. Vorynex never has to recognise anything: it denies the effect (the write, the connect, the exec, the read), not the request.

P3A real application, not our fixture

DVWS-node (GPL-3.0, maintained) in its own Docker stack: Mongo, MySQL, the app. Two genuine sinks — an authenticated exec() behind a normal login, and an unauthenticated XML-RPC fetch. The Vorynex column is Tier 1 armed on the running container's cgroup: no restart.

ScenarioBareCRS PL1CRS PL2CRS PL1 tunedVorynex Tier 1
rce_exec — id;touch … via /api/v2/sysinfo/:commandlandedlandedlandedlandedcontained
ssrf_uptime — XML-RPC fetch to the collectorlandedblocked*blocked*blocked*contained
ssti_env — ${process.env.SSTI_CANARY} via /api/v2/greeterlandedblocked**blocked**blocked**landed
benign_login — admin loginlandedlandedlandedlandedlanded
benign_info — GET /api/v1/infolandedlandedlandedlandedlanded

* Blocked by Coraza's body-parsing rule, not by an SSRF rule: CRS 4.0 has no XML body processor, so the request dies before any attack signature is evaluated. The tuned arm adds the JSON/XML processors a real deployment configures — the block persists for the same reason. Meanwhile the command injection passed every configuration; the audit shows no CRS rule matched it at all, because the payload is a path parameter and CRS scans arguments and a normalised URI.

** Blocked by rule 932130, which matches the shape ${…} in an argument — a signature on how the payload looks. That is the mirror of the row above it, and it is the most useful line in this report: the two approaches cover different classes. An in-process template evaluation produces no exec, no file open and no connection, so a runtime boundary has nothing to deny; an exec() injection in a path parameter produces no signature CRS recognises. A runtime boundary is not a substitute for fixing an injection sink, and a signature engine is not a substitute for containing what runs after one is exploited.

Tier 1 kept the application serving: both benign requests returned 200 inside the armed window, and the app was healthy after the hooks detached. The XML-RPC reply still said "Checking uptime for: …" while the collector logged zero hits — which is why the effect, not the response, is what gets measured.

Limits — what this does not show

  • The WAF arm is a stand-in. Coraza + OWASP CRS, not Cloudflare or Vercel: their free tiers cannot run the managed rulesets that matter, and bypasses are engine-and-framework specific. No commercial WAF is being described.
  • Three scenarios on the real app, and one of them is a measured failure: in-process data flows are out of scope for the hooks that were measured. XXE and NoSQL injection remain untested. The Tier 1 hooks were chosen by hand for these three attacks, not derived automatically.
  • Tier 0 is the tier measured for cost. Tier 1's hooks are per syscall — they are the arm most likely to show overhead, and they are not measured here. No throughput ceiling is claimed for any arm.
  • Small corpora. 7 attacks and 2 benign requests on the fixture; 2 and 2 on the real app. No false-positive rate is claimed; that needs a public benign corpus.
  • One machine, shared, over loopback, no TLS, with a trivial endpoint, at 200 rps, 7 rounds.
  • Out of scope by design: in-process RCE detection, root attackers, kernel exploits, serverless, application-level authorisation (IDOR/BOLA), and exfiltration over an egress the policy allows.

Reproduce

make proof        # P1+P2  — bare vs OWASP CRS vs Vorynex Tier 0   (also a CI job)
make proof-real   # P3     — DVWS-node in Docker; Tier 1 column needs root
make bench        # P4     — overhead, interleaved rounds, paired deltas

Each run writes raw evidence to tests/proof/evidence*/<stamp>/: per-arm JSONL, the CRS audit log with rule ids, summary.json, and an env.json recording the git SHA, kernel, and Landlock ABI. Full write-ups: docs/PROOF.md, docs/BENCHMARKS.md, docs/PERFORMANCE.md.

Vorynex — runtime containment. Enforcement is local and out of the request path; a compromise is contained rather than assumed to be blocked at the door.
